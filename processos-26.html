ATIVIDADE PROPOSTA

O que vocês vão resolver

Vocês vão explorar a segurança integrada ao pipeline em três etapas: primeiro configuram uma análise SAST (Bandit) no fluxo de Pull Request; depois interpretam o escaneamento de uma imagem Docker (CVEs) e aplicam hardening na imagem e no runtime; por fim, interpretam relatórios de duas ferramentas de segurança num pipeline de CI/CD — OWASP ZAP (aplicação) e Checkov (infraestrutura como código).

ENTENDA

DevSecOps – segurança integrada ao pipeline

Use o diagrama como mapa da atividade: ele mostra a estrutura que as respostas do grupo precisam seguir.

Quanto mais cedo uma falha é identificada, mais simples costuma ser a correção — o PR funciona como uma etapa de revisão de segurança.

Segurança em contêineres depende tanto da imagem usada quanto da forma como o contêiner é executado — corrigir só uma parte não elimina todos os riscos.

ZAP testa o comportamento real da aplicação rodando; Checkov revisa a infraestrutura antes mesmo de ela subir. As duas juntas ampliam a cobertura de segurança do pipeline.

PROCEDIMENTOS

Respondam passo a passo

1
Configuração da análise de segurança no Pull Request Contexto: em equipes de desenvolvimento, é comum configurar verificações automáticas para analisar o código antes da aprovação de um Pull Request (PR). Analisem a configuração simplificada abaixo para entender como uma ferramenta SAST, como o Bandit, pode ser integrada ao fluxo de revisão de código.
name: Security Check on: __________ jobs: security: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Executar Scanner run: __________
Como pensar: pensem em qual evento do GitHub dispara essa verificação (é sobre PR, não sobre todo commit), e qual seria o comando de terminal para rodar o Bandit num diretório.
2
Interpretando o scan de imagem Docker — análise geral Cenário: uma equipe pretende publicar uma aplicação usando Docker, mas identifica os seguintes riscos: a imagem possui pacotes com vulnerabilidades conhecidas; o contêiner será executado como root; existem dependências desnecessárias; algumas permissões estão abertas além do necessário.
Como pensar: um risco é "da imagem" quando já existe antes do contêiner iniciar; é "do runtime" quando depende de como o contêiner é executado.
3
Observando o resultado do scan A equipe executou: trivy image minha-aplicacao:latest
Target: minha-aplicacao:latest Total de vulnerabilidades: 5 CRITICAL: 1 HIGH: 2 MEDIUM: 2 Pacotes afetados: openssl, busybox, libxml2
Como pensar: os números já estão no resultado acima — expliquem o que eles significam para a equipe.
4
Aplicando hardening Depois da análise, a equipe decidiu reduzir os riscos nas duas esferas:
Na imagem: Usar imagem base mais enxuta. Remover dependências desnecessárias. Atualizar componentes vulneráveis. No runtime: Evitar executar o contêiner como root. Limitar privilégios. Revisar permissões e recursos expostos.
Como pensar: a lista já está organizada em "na imagem" e "no runtime" — usem essa organização para responder.
5
Fechamento — scan e hardening
6
Conhecendo as ferramentas Contexto: uma equipe usa um pipeline de CI/CD para verificar a segurança antes da publicação. Foram adicionadas duas ferramentas: OWASP ZAP, que analisa a aplicação em execução; e Checkov, que analisa arquivos de infraestrutura como código (IaC).
Como pensar: pensem em problemas que só aparecem com a aplicação rodando, e em problemas que já existem no arquivo de infraestrutura antes mesmo de rodar qualquer coisa.

Analisando um relatório do ZAP
OWASP ZAP Scan Report Medium Risk — Cross-Site Scripting (XSS) URL: http://localhost/login Status: Warning
Como pensar: revejam, no Passo 6, o que o ZAP analisa, antes de responder.

Analisando um relatório do Checkov
